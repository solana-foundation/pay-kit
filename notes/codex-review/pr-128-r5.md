## Findings

### P1 — None found.

### P2 — Client trusts challenge-supplied token metadata when signing. Confidence: 4 / 5
`python/src/x402/interop/exact.py` uses `decimals` and `tokenProgram` from the
payment requirement before falling back to RPC mint metadata. For a real client,
a malicious 402 challenge can influence the program id used in the signed
transaction. Safer behaviour is to always verify mint owner/decimals via RPC, or
only trust inline metadata in fixture/harness mode.

### P2 — Server does not bind the transfer token program to the accepted requirement. Confidence: 4 / 5
`python/src/x402/interop/server.py` accepts either `TOKEN_PROGRAM_ID` or
`TOKEN_2022_PROGRAM_ID` from the submitted transfer instruction, then derives
the destination ATA using that submitted program. It should also compare the
instruction program against `accepted.extra.tokenProgram`. Otherwise the server
can co-sign malformed/non-canonical payments and rely on RPC/preflight to
reject.

### P3 — Fee-payer exposure remains protocol-wide for unbounded CU limit + arbitrary Lighthouse optional instructions. Confidence: 3 / 5
The diff intentionally preserves Rust/TS parity, so this is not a
Python-specific regression. Still, the facilitator co-signs and pays fees while
`_verify_compute_limit_instruction` does not cap CU limit and Lighthouse
instructions are accepted without discriminator/account constraints. Track as a
spine-level hardening item, not a Python-only patch.

## Summary

The cross-spine wiring itself looks structurally sound: implementation IDs are
added consistently, the allowlist now correctly permits Rust ↔ Python canonical
pairs on both client and server side, the Python package is included in the
wheel (`packages = ["src/solana_mpp", "src/x402"]`), and the server has
meaningful coverage for replay, strict accepted-object matching, fee-payer
drain, signature, and malformed-payload paths.

Main residual risk is not the harness matrix; it is the trust boundaries around
challenge-provided token metadata and server-side token-program binding. Both
P2s are filed as follow-ups; neither blocks landing this PR because both are
also true of the Rust spine and need a coordinated fix (Codex r5 explicitly
calls this out as "spine-level hardening item, not a Python-only patch").
